# QuanYou Smart HomeCanvas

**全友·智绘家 —— 户型多模态装修推荐系统**

内江市全友家居 · 上传一张户型图 → 多模态解析 → 多 Agent 并行生成三套方案 → 预算估算 + 避坑审查 + 矢量户型图 + 3D 户型漫游。

> **状态**：**已通过初步验收**（2026-09-28）。验收标准里 **0 项未实现**（作废的几条都有决策记录）；
> 端到端清单 **2026-09-26 实测 22/22**；全量自动化测试 **1191 通过、0 跳过**（约 2 分钟，全程不联网）。
> 验收之后又补了两个模块（智友问答、屋主户型详情），并做了一轮界面文案清理 —— 详见项目说明书卷三。

---

## 这是什么

它不代替设计师做设计，也不代替业主做决定 —— 它做的是**把决策所需的信息摊开**：

```
户型解析线   上传户型图 → 质量预检(零Token) → 解析 → 五维诊断
                        → 矢量户型图 + 物品热区 + 地面材质替换
                        → 3D 漫游（第一人称行走 / 自由视角俯瞰）

方案生成线   三套方案并行（风格 × 档位）→ 每套三路并行
                        → 空间规划 / 预算造价 / 材料选型
                        → 汇聚避坑审查 → 横向对比矩阵 → 3D 装修漫游

避坑审查线   粘贴报价单 → RAG 检索依据 → 风险清单（8 类）
                        → 引用溯源 / 剔除编造引用 / 议价要点
```

面向三种角色，功能可见性由**后端强制**，不只是前端藏菜单：

| 角色 | 得到什么 |
|---|---|
| 业主 `user` | 诊断报告、三套方案对比、预算区间、报价单审查 |
| 设计师 `designer` | 多套风格×档位方案、材料清单、造价区间 |
| 管理员 `admin` | 知识库管理、性能指标、账号与额度管理 |

## 为什么值得看

**不是"用了 LangGraph 和 MCP"，而是每一项技术决策都带本机实测数据，
凡是实测推翻的就在文档里写明推翻理由。**

举三个例子：

- **放弃了「AI 出效果图」**。本机可用显存 3.22GB，但真正的问题不是显存 ——
  是任务错配：输入是俯视平面图，让人眼视角实景从平面图里长出来是研究级任务。
  四组对照实验定位到根因是结构性的（`controlnet_sd15_canny` 会逐边复刻俯视条件图）。
  交付物定义因此收窄为「**3D 户型渲染图**」，并在 UI、README、API 字段三处强制统一措辞。
- **不让 LLM 算钱，也不让它给坐标**。预算由纯函数规则引擎计算；3D 家具摆放由规则计算。
  理由一致：让模型产出这些，质量标准就只剩下"看起来合理"，而那正是本项目一路在防的东西。
- **3D 表面色是搜出来的，不是调出来的**。手工调七轮，约束全过、画面一团黑。
  改成约束下的搜索后，撞出三件事，其中一件是**算出来**的：
  在两个中性色上，"对地面 ≥2:1"与"两两 ΔE ≥6.6"在现行地面亮度下**数学上不可兼得**。

## 快速开始

```bash
# 1. 环境（本机唯一带 CUDA torch 的环境）
PY="D:/AI damoxing/Anaconda3/envs/pytorch/python.exe"

# 2. 配置（DEEPSEEK_API_KEY 留空则自动走本地 Ollama）
cp .env.example .env

# 3. 跑测试（不联网，conftest.py 有网络绊线）
$PY -m pytest tests/                        # 1191 passed, 1 deselected，约 2 分钟
```

> ⚠️ **其中 37 条落库/检查点用例需要 `psycopg[binary]` + `psycopg_pool` +
> `langgraph-checkpoint-postgres`，且 PostgreSQL 可达。** 缺任一条件它们会
> **跳过**（不是失败）。本机当前具备这些条件，**1191 条一条不跳**。
>
> 但**不要**把跳过当成"无所谓" —— 这 37 条曾经一次都没真正跑过：
> 本机 conda 环境没有 psycopg3（跳过）、容器里有 psycopg3 却没装 pytest，
> 而代码里还写着一个 **Python 3.12 才有的 `asyncio.run(loop_factory=...)`**
> （本项目与容器都是 3.11）。**两头都不执行，于是它们看起来是绿的。**
> 现已修正，并实测 37/37 通过。

```bash

# 4. 起后端（http://127.0.0.1:8000/docs 可交互调试）
$PY -m uvicorn backend.app.main:app --reload --port 8000

# 5. 起前端
cd frontend && npm run dev

# 6. 一键起全部容器（4 容器，全部绑 127.0.0.1）
docker compose up -d && docker compose ps
```

**演示账号**见 `seed_data/users.json`（管理员 / 设计师 / 普通用户各一，页面登录框也有列）。

**端到端验收**：

```bash
$PY scripts/e2e_smoke.py              # 逐条对真实产物断言（每条标了对应哪个 AC）
$PY scripts/review_sample_quote.py    # 避坑审查召回率（带标注样本）
$PY scripts/mcp_smoke.py              # MCP 三个工具走真实 stdio
```

## 技术架构

```
┌──────────────────────────────────────────────────────────┐
│ 接入层   Vue 3 + TypeScript + Vite 6 + Pinia + Tailwind   │
│          22 条路由 / 19 个页面 / 17 个组件                 │
└────────────────────────┬─────────────────────────────────┘
┌────────────────────────▼─────────────────────────────────┐
│ 服务层   FastAPI（异步）+ LangGraph 状态图                 │
│          6 个 Agent · 36 条接口 · 3 个 MCP Server          │
└────────────────────────┬─────────────────────────────────┘
┌────────────────────────▼─────────────────────────────────┐
│ 数据层   PostgreSQL 15 · Redis 7 · ChromaDB（嵌入式）      │
└────────────────────────┬─────────────────────────────────┘
┌────────────────────────▼─────────────────────────────────┐
│ 模型层   多模态：DeepSeek → minicpm-v4.6（本地）           │
│          文本：deepseek-flash → qwen2.5:3b（本地）         │
│          Embedding：bge-large-zh-v1.5（本地，1024 维）     │
│          图像：VectorRenderer（确定性矢量渲染）             │
└──────────────────────────────────────────────────────────┘
```

**LangGraph 工作流** —— 六个 Agent，三路并行 + 一次汇聚审查：

```
START → precheck_image → parse_layout → diagnose_layout
          │                                        │
          │    fan-out（Send）：3 套方案 × 3 个产出者 = 9 个并发任务
          │    ├─ generate_plan    A-03 空间规划
          │    ├─ estimate_budget  A-04 预算（规则引擎）
          │    └─ select_materials A-05 选材（代码回填价格）
          │                                        │
          ▼                                        ▼
       （不合格直接拒）                        review_risks  A-06 避坑审查
                                               ↑ 汇聚节点，不是并行分支
                                                │
                                          aggregate_plans → END
```

**A-06 为什么不在并行分支里**：**你没法审查一份还不存在的预算。**
并行的前提是互不依赖，而不是"看起来可以并行"。

**Docker 拓扑 4 容器**（`qy-postgres` / `qy-redis` / `qy-backend` / `qy-nginx`），
**四个端口全部绑 `127.0.0.1`** —— 本项目存用户上传的户型图，
`ports: ["5432:5432"]` 那种写法会把数据库暴露给整个局域网。

## 三条工程纪律

1. **禁止编造。** LLM 不得生成金额、坐标或浓度数字；识别不出就说识别不出。
2. **降级必须显式。** `degraded` 贯穿 API → 审计日志 → 前端 UI 三处。
   **静默降级视为缺陷** —— 用户有权知道这次结果来自本地小模型。
3. **不产出「看起来合理的错误」。** 降级时 `total_area = 0` 若放任流入下游，
   `calc_budget(area=0)` 会返回一个 **¥0 的预算且不报错** ——
   而用户会拿它去和装修公司谈。因此有业务连续性守卫在数据层拦截，
   且所有业务失败走 `HTTP 200 + code != 0`，拒绝时**必须说明缺什么以及如何修复**。

## 已知限制

本项目主动标注局限，而不是等评审发现：

| 限制 | 原因 | 处理 |
|---|---|---|
| **只做 3D 户型渲染图，不做室内实景效果图** | 输入俯视平面图转人眼视角是任务错配，实测失败 | 交付物定义收窄；措辞在 UI/文档/API 三处统一，有测试守着 |
| **两条性能目标不成立**：解析 P95 实测 **67.5s**（目标 < 20s）、方案生成实测 **112s**（目标 < 60s） | 解析那条是"两次 LLM 调用只按一次估"；方案生成那条是 A-06 汇聚节点串行约 39s 无影子可躲 | **不调低目标来"达标"** —— 如实记下"它不成立"，优化方向登记为 R-20 |
| 房间识别准确率**无法判定** | 没有标注测试集就没有分母 | 演示图实测能识别 9 间房，但**这是样本不是指标** |
| 3D 家具是体块，无 mesh 与贴图 | 无现成的中式家具模型库 | 明确标注，观感靠配色与比例 |
| 3D 约一半概率判为「不可贴地行走」 | 上游模型门检出率不是 100% | **把自由视角当默认**；不可达房间在界面上标灰并写明是哪一间 |
| **个别户型识别不到「通到户外的门」** | 有的图面上就没画入户门（演示图 03 就是），视觉模型也无法凭空读出一扇 | 认不出来时**如实说明**"围墙是整圈闭合的"，**不凭空补一扇门**（那会画出一条现实里不存在的通路）；能认出来的户型会在 3D 里画出并开洞 |
| **门中心自带 0.5～1.2m 的位置噪声** | 门是用开启弧估出来的，比窗（双线段）飘得多 | 挂墙容差按**解析自身的噪声量级**取（曾有离墙 1.11m 的门被 1.0m 的门槛整扇丢掉，连带可逛面积从 55% 掉到 45%） |
| 本地兜底只能读房间名 | 实测小模型会编造越界 bbox 与虚构墙体 | 质量闸门 + 能力守卫，**不假装完整** |
| 前端没有测试框架 | 无 vitest、无 `*.spec.ts` | 用后端契约测试 + 3D 数值探针替代；**已在验收表里逐条标注**（R-21） |
| **知识库只有"装修经验"一类语料** | 国标、全友官方语料从未入库（`status: pending`） | A-06 的结论能给经验文章出处，**引不到法条**（见下） |
| 全友产品为演示数据 | 无公开结构化价格接口 | 显著标注，不表述为真实报价 |
