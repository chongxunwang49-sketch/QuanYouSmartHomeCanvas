## 1. LangGraph `Send` 的 payload 是「替换」状态，不是「合并」

**日期 / 阶段**：2026-09-22 · 阶段1（M2 前半）· A-03 空间规划接入，链路扩展为 3 路并发 fan-out / fan-in

**一句话亮点**：官方的 map-reduce 示例恰好掩盖了一个语义陷阱；我先写 20 行探针验证，避免了三个分支一起在 Agent 里抛 `KeyError`。

**背景 / 问题**
接入 3 路并发 fan-out 时，A-03 分支需要从父状态读取 `layout` 与 `diagnosis`（A-01 / A-02 的产出）。
LangGraph 用 `Send` 做 fan-out，官方示例看起来像「把状态子集交给分支」，但 payload 到底是**替换**还是**合并**父状态，文档没有一句话说清。

**做法**
没有照抄官方 map-reduce 示例，先写了一个约 20 行的最小探针：父节点写入 `parent_only` / `seed` 两个字段后 fan-out，分支里读这两个字段。

**结果**
两个字段在分支里**全部缺失**，分支只看到 payload 里的键 —— 确认 payload **替换**整个节点输入状态。
官方示例之所以看不出差别，是因为它的分支节点恰好只用 payload 里的字段；**照抄必中招**，而且要等运行到 Agent 内部才抛 `KeyError`，错误现场离根因很远。

**修复**
`layout` / `diagnosis` / `requirements` / `task_id` 等分支真正会读的字段显式塞进每个 `Send` 的 payload（`_fan_out_plans` 里的 `shared`），并加防回归测试 `TestSendPayload::test_payload自带layout与diagnosis`；再反向测一条 `test_payload不带无关字段`，防止有人图省事把整份 state（含图像 base64）塞进去 —— payload 会随 checkpointer 序列化落盘，塞整份会让分支载荷放大 3 倍。

**为什么体现能力**
不是"会用框架"，而是**对不确定的框架行为先做最小验证、不靠猜**。我识别出"官方示例恰好绕开了这个差异"，并把结论固化成回归测试 —— 说明我知道这类语义约定一旦被误改，报错点会离根因很远。

**面试话术**
- 讲法："接 fan-out 时我没直接抄官方示例，先写了个 20 行探针确认 `Send` 的 payload 是替换还是合并 —— 结果是替换。官方示例恰好只用 payload 里的字段所以看不出差别，照抄的话要等三个分支一起在 Agent 里抛 `KeyError` 才发现。"
- 追问"怎么确认是替换不是合并" → 探针里父节点写入两个分支本不会用到的字段，分支里读它们是 None，只剩 payload 的键。
- 追问"那分支的回写呢" → 回写走正常 reducer 通道（`plan_bundles` 用 MergeDict、`trace` 用 `operator.add`）；反过来，`degraded` / `phase` 这类没有 reducer 的标量被三个分支同时写会直接抛 `InvalidUpdateError`，已在 state 层改成 `OrBool` / `LastWrite`。

## 2. 218 个测试全绿，但其中三个分支在偷偷打真实付费 API

**日期 / 阶段**：2026-09-22 · 阶段1 · A-03 接入后的测试治理

**一句话亮点**：测试全绿却从 ~20s 变成 108s —— 新增分支拿着真实 `LLMClient` 在并发打网络；这类「沉默的代价」不报错，只会一直烧钱。

**背景 / 问题**
接入 fan-out 后跑 `pytest`，耗时从约 20s 涨到 108s。测试**全部通过**、无一失败。

**根因**
`workflow._AGENTS` 是在 **import 时**构造的 Agent 实例，而测试 fixture 只替换了其中两个（A-01 / A-02）。新增的 `generate_plan` 节点仍持有**真实 `LLMClient`**，fan-out 后并发跑了三个实例，每个打了 9–11 秒真实 DeepSeek（日志可见 `[A-03] deepseek/deepseek-flash tokens=2925`）。

**关键点**
测试照样全绿 —— 不报错、不失败，只是慢、花钱、结果依赖网络，还顺手把测试数据发了出去。这类「沉默的代价」最贵：它不产红，只是让 CI 慢慢变慢、账单慢慢变高，直到某天有人发现。

**修复**
`conftest.py` 加了一条 autouse 网络绊线，在 **`httpx.AsyncClient` 这一层**拦截。选这一层是因为 `LLMClient` 的所有出站请求都经过它 —— 一处拦截覆盖全部路径（DeepSeek 的 `/v1` 与 `/anthropic`、以及本地 Ollama）。报错信息直接指向最可能的原因（"`workflow._AGENTS` 里有 Agent 没被替换成 Fake LLM"）和修法，并对 `@pytest.mark.integration` 显式放行（那些测试就是要打真实 API，不该被误伤）。

**结果**
测试回到 **14.6s**，全程不联网。

**为什么体现能力**
"测试通过"不等于"测试正确"。能从一个绿色的、只是变慢的信号里追出"测试在花钱"的根因，并给出**一处拦截、覆盖全部出网路径**的设计，而不是在每个测试里逐个打补丁。

**面试话术**
- 讲法："我给测试加了个网络绊线。背景是接完 fan-out 测试从 20s 变 108s、还全绿，但发现三个新分支拿着真实 LLM 在并发打 DeepSeek —— 因为 Agent 注册表是 import 时构造的，fixture 只替换了两个。这类问题不报错，只会一直烧钱。"
- 追问"为什么拦 httpx 而不是拦 `LLMClient`" → `LLMClient` 的所有出站都走 `httpx.AsyncClient`，拦在这一层一处覆盖全部路径、含本地 Ollama；拦在上层要逐个方法打补丁，容易漏。
- 追问"本地 Ollama 为什么也拦" → 测试不该依赖本机是否开着模型服务，否则机器不同结果不同。

## 3. `pytest.ini` 里写了「默认不跑」，但配置根本没生效

**日期 / 阶段**：2026-09-22 · 阶段1 · 与亮点 2 同批发现

**一句话亮点**：`markers` 里的说明只是**声明**、不是行为；`-m "not integration"` 没写进 `addopts`，日常 `pytest` 一直在打真实 API。

**背景 / 问题**
修完网络绊线后复查配置，发现 `pytest.ini` 里写着：

```ini
markers =
    integration: 需要真实外部依赖（网络 API / GPU / 数据库）的测试，默认不跑。
```

但 `addopts` 里**并没有** `-m "not integration"`。

**结论**
`markers` 段只是**给 marker 起名字、写说明**，pytest 不会因为它写了"默认不跑"就跳过。真正的执行范围只由 `addopts` / 命令行决定。也就是说，这个项目**此前每一次日常 `pytest` 都在跑集成测试、打真实 API** —— 而它一直是绿色的，没人发现。

**修复**
`addopts` 补上 `-m "not integration"`，并在同一处留注释说明"这一条必须留着"，防止后来者当成冗余删掉。

**为什么体现能力**
**配置里的注释 / 文档与实际生效的行为是两回事，要验证后者。** 这和"拿 `pip` 版本号判断行为""拿日志有没有出现判断成功"是同一类错误：用一个间接信号代替对真实行为的验证。发现它靠的不是工具，而是"配置写了 ≠ 生效了"这个意识。

**面试话术**
- 讲法："我们 `pytest.ini` 的 `markers` 里写着集成测试『默认不跑』，但 `addopts` 里没加 `-m "not integration"` —— 也就是那一刻起，日常 `pytest` 一直在打真实 API，而且一直全绿，没人发现。配置里的注释不等于生效的行为。"
- 追问"这类问题你怎么系统性地防" → 只认可观测的行为：测试耗时、出网记录、断言里的实际调用次数，而不是配置文本。必要时加"反向测试"（例如断言集成测试在默认模式下根本没被收集）。

## 4. 并发判定公式写错，脚本给出「疑似串行」的错误结论

**日期 / 阶段**：2026-09-22 · 阶段1 · `scripts/e2e_smoke.py` 建立时

**一句话亮点**：一个用于验证的脚本如果判据写错，比没有脚本更危险 —— 它会给出**看起来有依据**的错误结论，让人去"修"一个本来正常的东西。

**背景 / 问题**
新建的 `scripts/e2e_smoke.py` 要验证「3 个分支真的并发」。第一版公式：拿**总墙钟 53.2s** 去比 max 分支耗时 19.3s，比值约 2.8×，判定为"疑似串行"。

**真相**
总墙钟里含 A-01 的 15.7s 与 A-02 的 18.1s。
fan-out 阶段 = 53.2 − 15.7 − 18.1 = **19.4s ≈ max(19.3s)**，**是并发的**。

**修复**
判据改为量「fan-out 阶段时长 = 总墙钟 − 上游节点耗时」，再与 max 单分支求比值。实测 **1.00×**（并发时 ≈ 1.0，串行时会接近分支数）。脚本里留了醒目注释，说明为什么**不能拿总墙钟去比**。

**为什么体现能力**
先怀疑自己的测量口径，而不是去修一个本来正常的东西。同类问题的模式都是"用间接信号代替真实行为"：用 `pip` 版本号判断行为、用日志出现与否判断成功。

**面试话术**
- 讲法："我的端到端脚本第一版判『3 个分支并发』时是错的 —— 我拿总墙钟 53.2s 去除以最慢分支 19.3s，得出 2.8×、疑似串行。但总墙钟里含上游解析和诊断的 33.8s；把上游减掉，fan-out 阶段是 19.4s，几乎正好等于最慢分支，本来就是并发的。修好之后比值 1.00×。"
- 追问"为什么这值得一提" → 因为验证脚本写错比没有脚本更危险：它给出有数字支撑的错误结论。所以我后来对这类脚本的第一反应是"我的判据口径对吗"。

## 5. 幻觉房间：关键判定不交给模型的自觉

**日期 / 阶段**：2026-09-22 · 阶段1 · A-03 空间规划（schema + 后处理）

**一句话亮点**：给模型一个两居室，它照样能写出「儿童房」「书房」；所以房间对齐由代码逐一比对，模型不照做也拦得住。

**背景 / 问题**
A-03 空间规划时，模型语料里堆满"标准三室两厅"样板，给它两居室照样能写出「儿童房」「书房」，而且写得很像那么回事。这与 A-02 的"编造评分"同源：**模型被要求产出结构化内容时，倾向于先满足格式、再考虑事实**；提示词里写"不要编造"能减少但不能消除。

**做法（两层）**
- Schema 层：`ZonePlan.room_name` 的字段描述要求"**原样照抄户型数据中已存在的房间名**"（该描述会被原样拼进 Prompt，所以是写给模型看的）。
- 代码层：`_postprocess` 逐一比对 `zones` 与 `layout.rooms`，对不上的**剔除**并记入 `invented_rooms`。剔除 = 不存在的房间无法落地施工；记录 = 这是要暴露给开发者的质量信号，不能静默丢弃。同时反向补记遗漏房间到 `unassigned_rooms`。

**容错的松紧本身是个设计决策**
做了一组纯函数 `_match_room`：「客 厅」/「客厅(Living Room)」/「主卧室」都算**表述差异**、归一到户型原名、不计幻觉；而「房」这种单字**不参与**包含匹配（否则会把一堆房间误配到一起）。容错太松则每份方案都误报、信号失效；太紧则把模型的正常表述当成编造。

**边界纪律**
`SpacePlan` 在**类型层面就不含任何金额字段** —— 预算由 A-04 规则引擎算（ADR-07）。用类型系统固化"A-03 只做空间安排 / A-04 算钱"的职责边界，比在文档里写一句"注意不要报价"可靠得多。

**结果**
真实链路 e2e 实测 3/3 套方案房间对齐无误、无幻觉房间；`invented_rooms` / `unassigned_rooms` 同时作为数据质量信号带进对比表。

**为什么体现能力**
知道提示词只能降低概率、不能保证，于是把"关键判定"从模型转移到代码；并且对**误报 vs 漏报**做了取舍，而不是简单写死一个等值判断。

**面试话术**
- 讲法："空间规划里模型会编房间 —— 两居室能给你写出儿童房。我没指望提示词，代码层做了逐一比对，对不上的剔除并记入 `invented_rooms`。剔除是因为不存在的房间没法施工，记录是因为这是要暴露给开发者的质量信号，不能静默丢。"
- 追问"那正常表述差异会不会被误杀" → 专门的 `_match_room` 处理：「客 厅」「客厅(Living Room)」「主卧室」都归一到户型原名、不算幻觉；但单字「房」不参与包含匹配，避免把一堆房间误配到一起。容错松紧是权衡：太松信号失效，太紧把正常输出当编造。
- 追问"为什么不在提示词里解决" → 提示词降概率不保证；关键判定放在代码里，模型照做是好事、不照做也拦得住。

## 6. 一个只在「分支内出现第二个 Agent」时才暴露的静默数据丢失

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 预算接入（分支内由 1 个 Agent 变为 2 个）

**一句话亮点**：A-03 与 A-04 写同一个 `plan_id`，浅合并 reducer 把先写的那份**整个顶掉** —— 不报错、不告警、日志全绿，用户拿到一份只有预算没有空间规划的"方案"。

**背景 / 问题**
`backend/app/graph/state.py` 的 `_merge_dict` 原先是浅合并（`{**left, **right}`）。分支内只有一个 Agent 时它完全够用，所以从 A-03 接入起一直没暴露。A-03 与 A-04 并行写同一个 `plan_id` 后：

```
A-03 写  {"plan_x": {"space_plan": …}}
A-04 写  {"plan_x": {"budget":     …}}
浅合并   {"plan_x": {"budget": …}}      ← space_plan 消失
```

**做法：先写探针验证，再改代码**
容器/框架的 reducer 语义官方文档没有一句话说清，靠猜会猜错。写了一个约 15 行的独立脚本，用真实 `StateGraph` 复现这次并行写入，确认合并后 `"space_plan" in inner` 为 **False** —— 拿到了事实再动手。

**修复**
改为深合并一层（一层正好：`plan_bundles` 的结构就是 `{plan_id: {产物名: 内容}}` 两层，再往下递归反而会让两个分支往同名产物里写时互相污染），并在 `state.py` 就地写了长注释说明这个坑。配两条防回归测试：`test_同一plan_id下两个Agent的产物共存`（`tests/test_fanout.py`）与 `test_每套方案同时含规划与预算`（`tests/test_workflow.py`）。

**为什么体现能力**
这类**静默失败比崩溃危险得多**：没有异常、没有红色断言、没有告警，只是把方案正文丢了，而用户会拿着一份残缺的结果去做决策。另外值得讲的是「先探针后修」的工作方式 —— 对语义不确定的框架行为先做最小验证，而不是读文档猜或改完再看。

**可延伸**
`images` / `hotspots` 是同样的两层 dict 结构，因此一直存在同一个隐患，只是此前没有第二个 Agent 往同一个 key 里写。修 reducer 等于把这三个字段一起兜住了。

**面试话术**
- 讲法："接预算 Agent 时踩到一个不报错的 bug。分支里原本只有一个 Agent，状态用的浅合并够用；加了第二个之后，两个 Agent 并行写同一个 `plan_id`，浅合并直接把先写的空间规划整个顶掉了。用户会拿到一份只有预算、没有方案的'方案'，而日志全绿。"
- 追问"你怎么发现的" → 我没有先改代码，先写了个 15 行探针用真实 StateGraph 复现，确认合并后 `space_plan` 不存在，再改。
- 追问"为什么只深合并一层" → `plan_bundles` 就是 `{plan_id: {产物名: 内容}}` 两层，一层正好；再深会把两个分支写同名产物时的问题掩盖掉。

## 7. 用类型系统而不是提示词来执行一条 ADR

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 预算接入（ADR-07：预算数字由规则引擎计算，LLM 不得生成金额）

**一句话亮点**：把「LLM 不许写金额」从提示词里的一句请求，变成类型里**根本没有放数字的地方** —— 提示词是降低概率，类型是消除路径。

**背景 / 问题**
ADR-07 要求预算数字由规则引擎计算。最容易想到的做法是在提示词里写"不要给金额"，但那只是降低概率：模型想"顺手改个数"时依然有地方可写。

**做法：把它变成结构事实**
两组模型**从不互相赋值**：
- `BudgetBreakdown` —— 有金额字段，且只由 `services/budget/engine.py` 产出；
- `BudgetNarrative` —— 交给 LLM 的那部分，**一个数值字段都没有**（唯一例外是 `confidence`，它是"对这次文字解读的把握"，不是钱）。

模型即便想产出金额，也无处安放。

**测试守住这个结构事实**（`tests/test_budget_agent.py`）
- 遍历 `BudgetNarrative.model_fields` 的类型，用**允许清单**（`{"confidence"}`）而不是黑名单 —— 黑名单会随字段命名变化而失效，允许清单要求每个新增数值字段都被显式审过一次；并另有一条测试断言**允许清单本身没被悄悄扩大**。
- 再查一遍字段名里的金额词，判据只取明确指向钱的词（`amount` / `price` / `total` / `金额` / `单价` / `费用` / `总价`），**刻意不含 sum / cost** —— 否则 `summary`（含 sum）与 `cost_drivers`（描述成本构成的文字）会被误伤，那条测试就失去意义了。

**结果**
A-04 的预算数字与直接调引擎的结果**完全一致**（测试逐字段比对，差一分钱都算被改过）；模型即便在自由文本里写"这套大约 15 万"，也只停留在 `summary` 字段，进不了任何金额字段。

**为什么体现能力**
**提示词只能降低概率，类型能消除路径。** 同一项目里 A-03 也用了同样的手法（`SpacePlan` 不含金额字段），所以这不是一次性的技巧，而是本项目的一条可复用模式。这条对比在面试里很好用，也说明分得清"约束模型"与"让模型没有机会"。

**面试话术**
- 讲法："需求里有一条：预算数字必须由规则引擎算、LLM 不许生成金额。大家的直觉是在提示词里写'不要给金额'，但那只是降低概率。我把它做成了结构事实 —— 给 LLM 的 `BudgetNarrative` 里一个数值字段都没有，它想改也没地方放。测试里直接用允许清单遍历字段类型，允许清单本身还有一条测试守着不许悄悄扩大。"
- 追问"为什么用允许清单不用黑名单" → 黑名单会随字段命名变化失效；允许清单要求每个新增数值字段都被显式审一次。
- 追问"字段名检查会不会误伤" → 判据只取明确指向钱的词，刻意不含 sum / cost，否则 `summary` 和 `cost_drivers` 会被误判，测试就废了。

## 8. 失败方向是反的：计算型 Agent 与生成型 Agent 的架构差异

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 预算接入

**一句话亮点**：A-04 是整条链路上唯一「断网可用」的 Agent —— 把 LLM 彻底拿掉，预算表依然完整。

**背景 / 问题**
A-01 / A-02 / A-03 都是**生成型**：LLM 失败就是没产物，这是合理的。A-04 是**计算型**，产物分两层 —— 数字（规则引擎，零延迟零依赖）与文字（LLM，只做装饰）。两层混在一次调用里，就会让一次网络抖动白白损失掉本来不需要网络的那部分价值。

**做法**
执行顺序刻意是「**先算数、再写字**」，且写字那一步：
1. 有**独立的、更短的**超时 —— `NARRATIVE_TIMEOUT = 20s`，节点总超时 30s（并有测试断言 `NARRATIVE_TIMEOUT < BudgetAgent.timeout`，防止有人把它调成一样长）；
2. 任何异常都不向上抛，一律回退到模板文案；
3. 回退文案刻意朴素，不假装有观点 —— 只如实说明"预算文字解读未能生成"，`confidence` 置 0。降级在用户眼里是"少了一段解读"，而不是"多了一段胡说"。

**结果**
测试里用 `mode="raise"` 的假模型把 LLM 彻底拿掉，`subtotal_min`、`price_per_sqm_min`、`region_coefficient`、各分项金额**全部完好**，只是挂了 `narrative_degraded = True`。整条链路 8 条 trace，A-04 是唯一不受网络影响的节点。

**一次真实的回退验证**
接入过程中，`conftest.py` 的网络绊线**真的拦到了 A-04 的真实 `LLMClient`**（fixture 漏配了一个 Agent）。三个分支各自抛错并**优雅回退**，预算数字照常产出 —— 回退路径不是纸面上的设计，它被真实触发过一次。

**为什么体现能力**
体现的是"分清哪些产物依赖网络、哪些不依赖，并让不依赖的那部分**不受依赖部分拖累**"。反过来的设计（先调 LLM 再算钱）会让一次抖动带走全部价值。这是对失败方向的判断，不是对代码的装饰。

**面试话术**
- 讲法："前几个 Agent 都是生成型，LLM 挂了就没产物，合理。预算是计算型，产物分两层：数字由规则引擎算，文字是 LLM 写的装饰。所以我把顺序定成先算数再写字，写字有独立的更短超时、失败就回退模板 —— 它是全链路唯一断网可用的 Agent。测试里直接把假模型设成一调用就抛错，预算表仍然完整。"
- 追问"为什么单独设一个更短的超时" → 慢模型不能把已经算好的数字一起拖走，写字必须先于算数被放弃；还有一条测试守着这个阈值必须短于节点总超时。
- 追问"回退文案怎么写的" → 刻意朴素、不假装有观点，只如实说明解说未能生成，并标注降级，让用户知道少的是什么。

## 9. fan-in 按「分支规格」列方案，而不是按「碰巧活下来的产物」反推

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 接入后的 fan-in 重构

**一句话亮点**：**「数据的来源」决定「数据缺失时的行为」** —— 从产物反推身份，产物一缺身份就没了；从规格取身份，产物缺了身份还在。

**背景 / 问题**
原先 `aggregate_plans` 遍历 `plan_bundles`，只收集有 `space_plan` 的分支。分支内只有一个 Agent 时没问题；两个 Agent 独立成败之后，出现"只出了预算、没出方案"的分支 —— 它会被整个丢掉，**连带扔掉已经算好的预算**。

**修复**
方案身份改从 `build_branch_specs(state)` 来。三个好处：
1. **部分产出的分支被保留** —— "3 套里出了 2 套"是可用结果，"0 套"才是失败；
2. 缺哪个产物写进 `missing_artifacts` **显式标出**，而不是让字段静默为空 —— 前端据此标灰，用户据此知道"这套方案的预算还没算出来"；
3. **顺序天然正确**，连原先的排序代码都不需要了。

**结果**
`test_空间规划失败时预算仍在`：A-03 挂在 `plan_nordic_medium` 上，该方案的预算**依然在**（分项 ≥ 7），`missing_artifacts == ["space_plan"]`；`test_按分支顺序而非plan_id字典序`：三套方案顺序与请求顺序一致（字典序会得到"中式、现代、北欧"这种与请求无关的排列）。

**为什么体现能力**
这是**数据建模层面的判断，不是打补丁**。同一个问题在提示词、异常处理、UI 上都可以"打补丁"，但根因是"身份从哪来"。把身份从易失的产物挪到稳定的规格上，三个症状一次消失。

**面试话术**
- 讲法："分支里两个 Agent 各自成败之后，出现了一种只有预算、没有空间规划的方案。旧实现是遍历产物、只收集有空间规划的分支，于是这种分支被整个丢掉 —— 连已经算好的预算一起扔了。我把方案身份改成从分支规格来，产物算'内容'、规格定'身份'。副产品是顺序天然正确，原来的排序代码也不用要了。"
- 追问"缺产物怎么办" → 保留方案，把缺失项写进 `missing_artifacts` 显式标出，而不是让字段静默为空。
- 追问"为什么强调这个" → 数据的来源决定了它缺失时的行为：从产物反推身份，产物一缺身份就没了。

## 10. 报错误的原因，比报错本身更糟

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 接入后的真实 e2e 复盘

**一句话亮点**：三套方案都报「幻觉房间被剔除 1 个」，而被剔除的"卧室"在户型里**明明存在** —— 功能一直是对的，错的是给用户的解释。

**背景 / 问题**
真实 e2e 跑出三套方案**都**提示「幻觉房间被剔除 1 个: ['卧室（重复安排）']」，而"卧室"在户型里明明存在。

**根因**
A-03 的 `_postprocess` 把两类不同的问题混进了同一个 `invented_rooms`：① 户型里根本没有的房间（真幻觉）；② 同一房间被写了两遍（重复）。实测模型对同一间卧室同时输出了「卧室」与「主卧室」，归一后是同一个房间，于是第二份被判成重复 —— 但对外的话术是说"模型输出了户型中不存在的房间"。

**修复**
拆成 `invented_rooms` 与 `duplicate_zones` 两个字段，各自的 `data_gaps` 文案如实措辞（重复那条写"有 N 个房间被重复安排，已保留第一份"）。配测试 `test_表述差异导致的重复也归为重复`（`tests/test_space_planner.py`），其中一条断言是**不能出现"不存在的房间"这句话** —— 把"不许误报原因"也变成可执行断言。

**为什么体现能力**
这是一个**诚实性**问题而非功能问题：功能上（剔除多余 zone）一直是对的，错的是归因。而用户会据此判断"这个模型靠不靠谱" —— 一个错误的归因会让人对系统失去信任，比不报错更糟。这条也呼应本项目一直强调的"不产出看起来合理的错误"。

**面试话术**
- 讲法："真实链路跑出来三套方案都提示剔除了一个幻觉房间，说模型编了一个户型里不存在的房间 —— 而那个房间明明存在。查下来是模型把同一间卧室写了两个名字，归一后算重复，但代码把'重复'和'不存在'塞进了同一个字段。功能一直是对的，错的是解释。我把两者拆成两个字段，各自的文案如实措辞，并在测试里直接断言不能出现'不存在的房间'这句话。"
- 追问"这算 bug 吗" → 功能上不是，诚实性上是。用户靠这个提示判断系统靠不靠谱，错误的归因比不报错更损信任。
- 追问"怎么防止再犯" → 把"不许误报原因"写成断言，而不是写在文档里。

## 11. 并行 fan-out 的直接回报：加一整个 Agent，墙钟零增长

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 接入后的 `scripts/e2e_smoke.py` 实测

**一句话亮点**：加了一个 Agent，用户感知不到变慢 —— 具体数字是 **1.00×**，不是形容词。

**实测数据**（真实 DeepSeek，`scripts/e2e_smoke.py`）
- A-03 分支：`[15763, 14929, 19283]ms`（最慢 19.3s）
- A-04 分支：`[10327, 8763, 10016]ms`（最慢 10.3s）
- A-04 最慢 10.3s **<** A-03 最慢 19.3s → A-04 完全躲在 A-03 的影子里
- fan-out 阶段仍是 **19.3s**，比值 **1.00×** 于最慢任务，与只有 A-03 时（19.4s）几乎一致

**为什么体现能力**
这是"总耗时 = max(分支耗时) 而非 sum"的**具体数字证据**。面试里说"我加了一个 Agent 但用户感知不到变慢"比说"我用了 fan-out"有力得多 —— 前者是结果，后者只是工具。而且这个数字是我自己的 e2e 脚本量出来的，判据口径也专门修过（见亮点 4：不能用总墙钟去比）。

**面试话术**
- 讲法："接入预算 Agent 之后我跑了端到端实测：A-03 分支最慢 19.3 秒，A-04 最慢 10.3 秒，后者的全部耗时都躲在前者影子里，fan-out 阶段仍然是 19.3 秒、比值 1.00×，和只有 A-03 时的 19.4 秒几乎一样。也就是说我加了一个 Agent，用户的墙钟时间没有变。"
- 追问"最大值怎么保证" → LangGraph 的 fan-out 用 `Send` 展开，分支真并发；脚本里的比值判据是 `fan-out 阶段时长 / 最慢分支`，并发时 ≈1.0、串行时会接近分支数。
- 追问"这个数字会不会只是这次恰好" → 三个分支各自独立发出，A-04 的耗时上限由它的独立超时（20s）与实现复杂度决定，只要不超过最慢的 A-03 就不进关键路径。

## 12. 把「价格表必须符合文档口径」变成可执行的断言

**日期 / 阶段**：2026-09-22 · 阶段1 · A-04 预算接入（价格表 `seed_data/pricing_demo.json`）

**一句话亮点**：价格表是自己建的、需求文档的区间是别人定的 —— 两条口径之间的关系用测试钉住，而不是靠人记得；顺带记录一次「判据写错会让正确代码报错」的小翻车。

**背景 / 问题**
三档的区间（¥800-1200 / 1500-2000 / 2500-3500 每平米）来自需求文档 2.2.2，但价格表是自制数据（`seed_data/pricing_demo.json`），**很容易慢慢跑偏**，而且跑偏了不报错。

**做法**
1. `tests/test_budget_engine.py` 里一组参数化测试断言「按本表算出的折合单价必须落在文档区间内」。改单价改歪了立刻报红，而不是等做完演示才被人发现"经济档怎么要 1500 一平"。另加一条：折合单价必须与面积无关（档位区间是按元/㎡ 定义的，出现非线性项就说明与"面积 × 单价"的口径不符）。
2. **架构测试**：读引擎源码的 AST，断言它没有导入任何 LLM / HTTP 模块（`llm_client` / `openai` / `anthropic` / `httpx` / `requests` / `ollama` / `mcp`），且没有 async 函数 —— 用不变量代替自觉，守的是 ADR-07。

**一次判据翻车（也值得讲）**
第一版用全文正则，结果在**引擎自己的文档字符串**里匹配到了「llm_client」这个词（注释里写着"不导入 llm_client"），把正确的代码判成违规。改为 AST 解析 `Import` / `ImportFrom` 节点 —— **判据必须是导入语句，而不是出现过这个词**。教训：**判据写错会让正确的代码报错，那比漏报更浪费时间**（与亮点 4 的"脚本判据写错"同类）。

**为什么体现能力**
知道"文档口径"和"数据文件"是两个会各自漂移的东西，于是把二者的一致性变成断言；并且知道静态检查要检查**行为**（导入）而不是**文本**（出现过这个词）。这两件事都不是业务功能，但都是工程可靠性的来源。

**面试话术**
- 讲法："我们三档预算的区间是需求文档定的 800-1200 / 1500-2000 / 2500-3500 每平米，但价格表是我们自己建的数据，很容易慢慢跑偏。我用一组参数化测试把'按本表算出的折合单价必须落在文档区间内'钉住，改单价改歪了立刻报红。"
- 追问"怎么保证预算数字不是模型算的" → 有一条架构测试直接读引擎源码的 AST，断言它没有导入任何 LLM / HTTP 模块、也没有 async 函数 —— 连 `llm_client` 都导不进来，就不可能在某次顺手优化里悄悄调模型。
- 追问"这个 AST 测试写过坑吗" → 第一版用全文正则，在自己的文档字符串里匹配到了「llm_client」这个词，把正确的代码判成违规。判据必须是导入语句而不是出现过这个词 —— 判据写错会让正确的代码报错，比漏报更浪费时间。

## 13. 先让指标「可测」，再谈达标 —— 测数据构成，而不只测代码

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 材料选型接入（AC-18：方案中全友产品覆盖率 ≥ 60%）

**一句话亮点**：一条 60% 的指标，如果候选集里全是全友，它恒为 100% —— 我先确认这条线还**测得出来**，再让它达标。

**背景 / 问题**
AC-18 要求「方案中全友产品覆盖率 ≥ 60%」。这条指标要成立，有一个容易被忽略的前提：**候选集里必须有竞品**。若目录里全是全友，覆盖率恒为 100%，一个「随便选」的实现也能过线，指标失去区分能力 —— 而它依然会持续给出绿色的假信号。

**做法**
1. 材料目录（`seed_data/material_catalog.json`）刻意保持每个品类 2 个全友 + 2 个竞品，7 个品类共 28 件、全友恰好 14 件，占比 **50%**。随机选择的期望覆盖率就是 50%，**低于 60% 的线** —— 必须真的优先选全友才过得去。
2. 更关键的一步：写了两条**测数据构成、而不是测代码**的测试（`tests/test_material_catalog.py`）：`test_目录里必须有竞品`、`test_随机选的期望覆盖率低于AC18门槛`。哪天有人往目录里塞满全友产品，这两条会报红，提醒他 AC-18 正在被稀释。

**结果 / 诚实补充**
真实 e2e 实测三套方案的全友覆盖率**都是 100%** —— 因为确定性打分给了全友 1.5 的偏好加分（`QUANYOU_PREFERENCE_BONUS`），排序上本就把全友排在前面。所以 60% 这条线在实践中是**下限保险**，而不是「刚好卡住」。它真正起作用的是模型做出偏离选择时的**代码兜底**（见第 15 章，有测试 `test_全选竞品时由代码补足` 覆盖）。

**为什么体现能力**
大多数人对「指标」的处理是把它实现出来就完了，很少回头问「这个指标还测得出来吗」。**指标被数据稀释掉，比没有指标更危险** —— 它会持续给出绿色的假信号。这类「元测试」（对测试有效性的测试）在质量体系里是必需的：它守的不是代码，是指标的可判别性。

**面试话术**
- 讲法："AC-18 要求方案里全友产品覆盖率不低于 60%。我先没写实现，先问了一句：这个数字还测得出来吗？如果目录里全是全友，它恒等于 100%，随便选都能过。所以我刻意让目录保持每个品类两个全友两个竞品、整体恰好 50%，随机选过不了线；还写了两条测试专门盯着目录构成，谁把目录塞满全友，测试就报红。"
- 追问"那实测覆盖率是多少" → 三套都是 100%，因为打分里全友有 1.5 的偏好加分，排序天然靠前。所以 60% 是下限保险；真正起作用的是模型偏离时的代码兜底。
- 追问"为什么不干脆把门槛提到 80%" → 门槛要跟「随机能拿到多少」挂钩才有意义。当前随机期望是 50%，60% 已经是必须主动优选才达得到的位置。

## 14. 模型只能「指认」，不能「创造」—— 并且这已成本项目的一条模式

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 材料选型接入

**一句话亮点**：材料方案的输出拆成三层，模型那层**一个数值字段都没有** —— 它想编一个价格，也没地方放。

**背景 / 问题**
材料推荐最容易出的问题不是选错，而是**编造**：编一个不存在的型号、编一个看起来合理的价格、编一个官网搜不到的链接。而用户会拿它去下单。提示词里写「不得编造」只是降低概率。

**做法（三层）**
① `choices`（选了哪个 id、为什么）← **LLM**；
② 名称 / 品牌 / 价格 / 链接 ← **代码**按 id 从目录回填（`catalog.by_id()`）；
③ `quanyou_coverage` / `invented_products` ← **代码**计算。
`MaterialPlan`（模型那层）除 `confidence` 外**没有任何数值字段**，测试用允许清单遍历字段类型把这一点钉住；id 不在候选集里的一律剔除并记入 `invented_products` —— 包括「真实存在但不属于本档」的（经济档选了高端岩板，那是在偷偷超预算）。

**它已经是模式，不是技巧**
同一手法在本项目出现过四次：A-02 对数据不足的维度强制标记 `insufficient_data`；A-03 剔除幻觉房间；A-04 用 `BudgetNarrative` 封死 ADR-07（预算数字不得由 LLM 生成）；A-05 的 `MaterialPlan` 封死价格。**凡是会产出「看起来合理的错误数据」的地方，都从类型或流程层面断掉路径，而不是在提示词里叮嘱。**

**结果**
`test_价格与链接来自目录` 逐字段比对回填值；`test_模型写的价格字段不会被采纳` 里模型在 summary 写「这套一共 8000 元」—— 这句话原样保留在自由文本里，**进不了任何结构化金额字段**。

**为什么体现能力**
面试时讲「我在这个项目里反复用同一个手法解决了四个不同问题」，比讲单个实现有力得多 —— 前者是方法论，后者是体力活。它也说明我分得清「约束模型」和「让模型没有机会」。

**面试话术**
- 讲法："材料推荐最怕的不是选错，是编造 —— 编型号、编价格、编链接。我把输出拆成三层：选谁、为什么由模型给；名称价格链接由代码按 id 从目录回填；覆盖率由代码算。给模型的那个 schema 里除了置信度没有任何数值字段，它想写价格也没地方写。"
- 追问"这是不是只在这一处这么干" → 不是。A-02 强制标记数据不足、A-03 剔除幻觉房间、A-04 用类型封死「预算数字不许 LLM 生成」，都是同一手法，已经是这个项目的模式。
- 追问"为什么不在提示词里强调" → 提示词降低概率，类型消除路径。关键判定不该交给模型的自觉。

## 15. AC-18 的代码兜底：不为了凑指标，换规格不符的东西

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 材料选型接入（AC-18）

**一句话亮点**：覆盖率不达标时代码自动替换 —— 但**找不到等价物就如实报未达标**。宁可数字难看，也不为了指标换一个规格不符的东西。

**背景 / 问题**
覆盖率必须由**代码**统计：让模型自报「我推荐了 80% 全友」等于让它给自己打分。但统计出不达标之后怎么办？

**做法**
1. 不达标时，代码在同品类里找一件**未被选中**的全友等价物替换（`catalog.find_quanyou_alternative`，受档位 / 风格 / 需求约束）。
2. 每一次替换**逐条记入 `auto_substitutions`**（改了什么、从哪换到哪、为什么），并写进 `data_gaps` —— 替换必须透明，不能悄悄改掉用户的方案。
3. 关键取舍：**找不到可替换的，就保留原选择并如实上报 `quanyou_met=false`**。

**结果**
`test_全选竞品时由代码补足`：模型全选竞品，覆盖率被补到 1.0，`auto_substitutions` 两条、替换原因可读。
`test_无全友可换时如实不达标`：用 monkeypatch 把「找不到替代」这条分支打桩出来，断言 items **不被清空**、`quanyou_met is False` —— 那条路径平时走不到，但必须诚实处理。

**为什么体现能力**
这是「**指标服务于目标，还是目标服务于指标**」的判断。需求要的是「优先用自家的东西」，不是「让那个百分比好看」。为了让一个数字达标而牺牲实际质量，是工程里很常见的堕落路径 —— 我在代码里把这个诱惑切断了，并且专门为这条分支写了测试。

**面试话术**
- 讲法："AC-18 的覆盖率由代码算，不达标就由代码在同品类里换成全友。但我加了一条：如果找不到合适的全友等价物，就保留原选择、如实报未达标，不硬凑。因为需求要的是『优先用自家产品』，不是『让那个百分比好看』。"
- 追问"这种分支怎么测" → 目录里每个品类都有全友，这条分支平时走不到，我用 monkeypatch 把 `find_quanyou_alternative` 打桩成返回 None，断言候选不被清空且 `quanyou_met=False`。
- 追问"替换会不会让用户觉得被摆布" → 每一次替换都逐条记进 `auto_substitutions` 并写进 `data_gaps`，改了什么、为什么改，用户看得到。

## 16. 不做向量检索 —— 一个写进代码注释里的技术取舍

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 材料选型接入

**一句话亮点**：需求文档写的是「RAG + 全友产品知识库」，我判断这个模块**用不上向量** —— 在一个 AI 项目里主动选择不用 AI，并把理由写进代码。

**背景 / 问题**
需求文档把材料选型 Agent 的技术实现写成「RAG + 全友产品知识库」，听起来就该上 embedding + Chroma。

**判断**
看数据形态就会发现用不上：用户偏好是**结构化**的（`has_children` 是布尔字段，`eco_level` 是枚举），商品也是打标好的（`suitable_for` / `style_fit` / `budget_grade`）。两边都是标签，匹配就是集合运算。而引入向量的代价是实打实的：多一个 Ollama 依赖、多一次网络往返、**结果不确定、无法断言「给定输入必然得到给定输出」**。

**决定**
本模块保持确定性（`catalog.py` 全是纯函数）。真正的语义检索留给 A-06 避坑审查 —— 那边的语料是装修规范与避坑文档，自由文本、无标签，才是 RAG 不可替代的地方（属于需求文档路线图的 M4 阶段）。

**佐证**
`tests/test_material_catalog.py` 里有一条**架构测试**：读源码 AST，断言 `catalog.py` 没有导入任何 LLM / 网络 / 向量相关模块（`llm_client` / `openai` / `anthropic` / `httpx` / `requests` / `ollama` / `chromadb` / `langchain`），且没有任何 async 函数。用不变量代替自觉。

**为什么体现能力**
这比堆技术栈更能体现判断力：**能说清「这里不需要什么」，比能说清「这里用了什么」难。** 而且它是有代价的取舍 —— 放弃了「我们用了 RAG」这个叙事，不是偷懒。判据是数据形态（有标签 vs 自由文本），不是技术时髦度。

**面试话术**
- 讲法："需求文档给材料选型写的是 RAG 加产品知识库，听起来该上向量库。但我看数据形态就发现用不上：用户偏好是结构化布尔字段，商品也都是打好的标签，匹配就是集合运算。引入向量反而多一个依赖、多一次网络往返，还失去『给定输入必然得到给定输出』这个性质 —— 那个模块的测试就没法断言了。"
- 追问"那真正的 RAG 用在哪" → A-06 避坑审查，那边是装修规范与避坑文档，自由文本、无标签，那才是向量不可替代的地方。
- 追问"怎么保证后来者不会顺手加回来" → 有一条架构测试读源码 AST，断言这个模块没导入任何 LLM / 网络 / 向量模块、也没有 async 函数。

## 17. 失败方向与 A-04 一致 —— 而这次的一致性是测试逼出来的

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 材料选型接入

**一句话亮点**：A-05 的 LLM 挂了，选材结果**依然完整** —— 这个兜底不是一开始设计好的，是写测试时发现「两个 Agent 的失败方向不一致」才回头补上的。

**背景 / 问题**
A-04 的 LLM 挂了，预算数字还在（先算数、再写字）；但 A-05 一开始没有兜底，LLM 挂了整个节点就没了。同一个项目里两个 Agent 的失败方向不一致 —— 这不是有意设计，是漏了。

**做法**
候选排序（`catalog.candidates`）本身已经编码了档位过滤、风格匹配、需求适配与全友优先，**不需要模型参与**。所以模型抛错 / 超时 / 返回空载荷时，回退确定性排序：取各品类打分最高的候选，理由直接复用评分时算出的 `reasons`（如「全友自有产品、风格匹配（nordic）」）—— **兜底结果依然是有依据的**，不是随便填一个；输出里标明「模型不可用，按匹配度自动选出」。`SELECT_TIMEOUT = 22s` 独立于节点总超时 30s，让兜底先于熔断发生（有测试断言 `SELECT_TIMEOUT < MaterialAgent.timeout`）。

**结果**
`test_模型抛错时仍产出选材`：模型 `mode="raise"`，items 依然完整且全为全友；`test_兜底理由仍有依据`：每项 reason 都非空并标明来源；`test_超时走兜底而非熔断`：把 `SELECT_TIMEOUT` 压到 0.05s 制造超时，选材照旧产出。

**为什么体现能力**
与 A-04「先算数、再写字」是同一条纪律：**把不依赖模型的那部分产物保护起来，不让它被模型的失败拖走。** 区别只是 A-04 保住的是数字，A-05 保住的是选择。更值得讲的是过程 —— 「失败方向是否一贯」这个判断习惯，是被测试逼出来的，而不是我一开始就想周全了。

**面试话术**
- 讲法："写 A-05 测试时我发现一个不一致：A-04 的模型挂了，预算数字还在；A-05 的模型挂了，整个选材就没了。都是『模型不可用』，两个 Agent 的失败方向却不一样。我回头给 A-05 补了确定性兜底 —— 候选排序本来就是确定性的，不依赖模型。"
- 追问"兜底结果会不会很水" → 兜底取的是该品类打分最高的候选，理由直接复用评分时算出的 reasons，所以它仍然有依据，只是少了点针对性。
- 追问"为什么单独设 22 秒超时" → 节点总超时是 30 秒，选材超时必须更早触发，才能兜底而不是被熔断拖走；有一条测试守着这个大小关系。

## 18. 从「加个 Agent 要改三处」到「只改一处」

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 接入时暴露，随即修复

**一句话亮点**：加 A-05 时我在 fan-in 里漏了一个硬编码的键，直接 KeyError —— 于是把「三处平行维护」改成「一张表派生」。

**背景 / 问题**
节点名与产物键此前是两张平行的元组，fan-in 的收集逻辑里还硬编码了一遍产物键。加 A-05（`select_materials` → `materials`）时漏了一处，`aggregate_plans` 里只收集 `space_plan` 与 `budget`，运行即 KeyError。

**修复**
改为从一张表 `_BRANCH_AGENTS`（节点名 → 产物键）派生：节点列表 `_BRANCH_NODES`、产物列表 `BRANCH_ARTIFACTS`、fan-in 的收集逻辑全部跟着这张表走，并在注释里写明「加分支 Agent 只需要改这一处」。

**结果**
`aggregate_plans` 里现在是 `artifacts = {key: bundle.get(key) for key in BRANCH_ARTIFACTS}` —— 新增产物自动被收集、自动进 `missing_artifacts` 判定，不可能再漏。

**为什么体现能力**
**「加一个东西要改几处」是衡量抽象质量的一把好尺子。** 改三处意味着三处会各自漂移，总有一天不一致；改一处意味着不可能漏。更值得讲的是：我没有把它当 bug 就地修掉，而是顺着症状找到「平行维护的两张表」这个根因 —— 与第 9 章 fan-in 的身份来源是同一种思路：把会漂移的东西变成单一来源。

**面试话术**
- 讲法："加材料 Agent 时我踩了个 KeyError：节点名和产物键以前是两张平行维护的列表，fan-in 的收集逻辑里还硬编码了一遍，我漏改了其中一处。我没有就地补上那个键，而是把它们合并成一张表，节点列表、产物列表、汇总逻辑全从这张表派生 —— 现在是『加一个 Agent 只改一处』。"
- 追问"为什么这个值得讲" → 「加一个东西要改几处」是衡量抽象质量的一把尺子：改三处会各自漂移，改一处不可能漏。
- 追问"派生会不会让代码更难读" → 那张表本身带注释说明每列含义，比三处平行列表更容易看出它们本该一致。

## 19. 上游数据有问题时，如实说 —— 而不是装作没看见

**日期 / 阶段**：2026-09-22 · 阶段1 · 真实 e2e 复盘（A-01 → A-03 的数据链路）

**一句话亮点**：上游把两个房间都叫「卧室」，下游会**静默丢掉一间** —— 名字是上游给的、我修不了，但我必须说出来。

**背景 / 问题**
真实 e2e 跑出三套方案**都**提示「重复安排被去掉 1 个: ['卧室']」。查下来根因在上游：A-01 把两个房间**都**命名为「卧室」（没区分主卧 / 次卧）。而 A-03 的 `covered` 集合只能表示「有个叫卧室的房间被安排了」，第二个同名房间既被判成重复、又不在 `unassigned_rooms` 里 —— **等于凭空消失**。

**做法**
名字是上游给的，本 Agent 修不了，但要如实上报：把上游同名房间单独识别出来（`dup_names`），在 `data_gaps` 里写明「户型数据中有同名房间（卧室），系统无法区分它们，方案中同一名称只会安排一次 —— 建议重新上传更清晰的户型图，或自行区分主次」。并且**不把这件事算成「模型写重了」**（它是被上游误导的）：`duplicates` 那句文案只在没有同名房间时才出现，措辞与 `based_on.rooms_total` vs `rooms_planned` 的差距合起来把情况讲清楚。

**为什么体现能力**
用户看到「两间卧室」却只拿到一间房的规划，如果系统不说，他会以为方案漏了。这类「**上游数据缺陷导致下游静默丢失**」的问题，在分布式 / 多 Agent 系统里非常常见 —— 能主动发现它、并且分清「这是谁的账」，是工程成熟度的体现。这与第 10 章「报错误的原因比报错本身更糟」是同一条纪律。

**面试话术**
- 讲法："真实链路跑出来三套方案都提示有个房间被去重了，查下来是上游把两个房间都命名成『卧室』。下游只有房间名这一个身份维度，第二个同名房间会被判重复、又不算『未安排』，等于凭空消失。名字不归我改，但我在 data_gaps 里如实说明：户型数据存在同名房间，系统无法区分，建议重新上传或自行区分主次。"
- 追问"为什么不算模型的错" → 模型是被上游数据误导的。报错误的原因比报错本身更糟，所以我没有把它计进「重复安排」那句文案。
- 追问"怎么让用户知道丢了一间" → `based_on.rooms_total` 与 `rooms_planned` 的差距连同 `data_gaps` 一起给到用户，前端据此标出来。

## 20. 并行 fan-out 的回报（第二次验证）：加第三个分支 Agent，墙钟几乎没变

**日期 / 阶段**：2026-09-22 · 阶段1 · A-05 接入后的 `scripts/e2e_smoke.py` 实测

**一句话亮点**：分支 Agent 从 2 个加到 3 个，fan-out 阶段仍是 15.6s，总墙钟 59.8s（加 A-05 前 58.8s）—— 这不是巧合，是 fan-out 的结构性质。

**实测数据（真实 DeepSeek，`scripts/e2e_smoke.py`）**
- A-03 分支 `[13276, 14228, 15572]ms`（最慢 **15.6s**）
- A-04 分支 `[8926, 12217, 12788]ms`（最慢 12.8s）
- A-05 分支 `[8053, 14228, 7864]ms`（最慢 14.2s）
- A-04 与 A-05 的最慢值**都低于** A-03 的最慢值 → 两个新 Agent 都躲在 A-03 的影子里
- fan-out 阶段仍是 **15.6s**；总墙钟 **59.8s**（加 A-05 前 58.8s），基本没变

**为什么值得讲**
这是「总耗时 = max(分支耗时) 而非 sum」的**第二次**实测验证 —— 第 11 章已经就 A-04 讲过一次。可以说：「这不是巧合，是 fan-out 的结构性质：**只要新 Agent 的耗时不超过最慢的那个，用户就感知不到它被加进来。**」第一次是观察，第二次才构成规律；而量它的判据口径本身也是修过的（见第 4 章：不能用总墙钟去比）。

**面试话术**
- 讲法："分支 Agent 从两个加到三个之后，我又跑了一次端到端：A-03 最慢 15.6 秒，A-04 是 12.8 秒，A-05 是 14.2 秒，后两个都在前者的影子里；fan-out 阶段还是 15.6 秒，总墙钟从 58.8 秒到 59.8 秒，基本没动。"
- 追问"每次都这么幸运吗" → 不是幸运，是结构性质：总耗时等于最慢分支，只要新 Agent 不超过它就不进关键路径。第二次实测得到同样结论，才算规律而不只是巧合。
- 追问"这个数字怎么量的" → e2e 脚本量的是「fan-out 阶段时长 = 总墙钟 − 上游节点耗时」，再除以最慢分支。第一版判据用总墙钟去除，得出了「疑似串行」的错误结论，后来修过（第 4 章）。

## 21. 审查者不能与产出者并行 —— A-06 必须是汇聚节点（并留下真实代价）

**日期 / 阶段**：2026-09-22 · 阶段1（M2 前半）· A-06 避坑审查接入

**一句话亮点**：需求文档画的是「四个 Agent 并行」，我判断其中一个不该并行 —— 因为**你没法审查一份还不存在的预算**；顺手把它提炼成一条可复用原则，并如实留下了它的代价。

**背景 / 问题**
需求文档 3.3 的状态图把「空间规划 / 预算 / 材料 / 避坑」画成四路并行。但 A-01~A-05 都在**产出**（解析 / 诊断 / 规划 / 预算 / 选材），彼此互不依赖；A-06 是**审查者** —— 它的审查对象（预算）必须先存在。若把它塞进并行分支，它会在预算还没算出来时拿到空表，要么报错、要么对着空表**编风险**。

**做法：先探针，再改图**
把它做成**汇聚节点**（三个产出者 → 审查 → fan-in），而不是第四个并行分支：

```
generate_plan ─┐
estimate_budget ├─→ review_risks (A-06) ─→ aggregate_plans
select_materials┘
```

关键的一步是**没有直接改图**。LangGraph 里「多个 `Send` 分派的任务指向同一节点时会怎样」没有一句话说清，所以我先写了两个探针脚本（3 任务 / 6 任务，模拟「3 套方案 × 1 / 2 种节点类型」）确认了两件事：该节点**只执行一次**，且能看到**全部合并后的写入**。拿到这个事实才动手。接入 A-05 后真实图上变成 9 个产出任务汇聚，同一结论再次成立（源码注释里记着这个数）。

**结果**
`workflow.py` 里审查者单独登记在 `_REVIEW_NODE`，**不混进**产出者表 `_BRANCH_PRODUCERS` —— 这个区分有测试守着，防止后来者顺手把 A-06 加回并行列表。

**代价（如实讲，这是本条的重点之一）**
A-06 成了**唯一拖慢墙钟的 Agent**。产出者互相并行，新加一个只要不慢过最慢的那个就"零成本"（第 11、20 章两次实测）；但审查是汇聚节点，**它的 38.76s 直接加到总时间上** —— 总墙钟 **59.8s → 111.3s**。这是"依赖关系决定架构"的真实成本，也是下一步最值得优化的地方（比如让审查只跑一次而不是逐方案跑）。

**为什么体现能力**
这与 **ADR-08**（图像节点移出并行分支，因为 3 路并发调图会打爆显存）是**同一类修正**。所以它不是一次孤立的改动，而是一条原则：**并行的前提是互不依赖，而不是"看起来可以并行"**。另外，先探针后改图的顺序也是本项目的一条惯用做法（第 1、6 章同款）。

**面试话术**
- 讲法："需求文档给避坑审查画的是四路并行，但我判断它不能并行 —— 前五个 Agent 都在产出、互不依赖，审查者要审的预算必须先存在。所以我把它做成汇聚节点，三个产出者全完成后它执行一次。改图之前我先写了两个探针确认 LangGraph 的语义：多个 Send 分派到同一节点时，它只执行一次、且能看到全部合并后的写入。"
- 追问"这样做有什么代价" → 它是唯一拖慢墙钟的 Agent。产出者并行时加一个只要不慢过最慢的就零成本，但审查是汇聚，实测 38.76 秒直接加到总时间上，总墙钟从 59.8 秒变成 111.3 秒。这是真实的取舍，我也把它写进了文档和 README。
- 追问"这和你们别的决策像吗" → 和 ADR-08 是同一类：图像节点本来也在并行分支里，实测 3 路并发调图会打爆显存，于是移到 fan-in 之后。两次都是同一个判断：并行的前提是互不依赖。
- 追问"如果非要把审查也做快呢" → 可以让审查只对「对比表选定的一套」执行而不是逐方案执行，或把它改成异步后置 —— 但那会改变交付语义，不是纯性能优化，需要产品侧决策。

## 22. 引用走「指认」而非「生成」—— 杜绝"看起来像引用但查不到"

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 避坑审查接入（AC-06：引用知识库来源）

**一句话亮点**：AC-06 要求引用来源，我让模型**只能指认编号**、由代码映射真实出处 —— 每条风险**要么能追溯到具体语料，要么明确没有来源**，不存在中间态。

**背景 / 问题**
若让模型自由写来源（"参考行业规范"），那条引用**不可验证**；更糟的是模型可能编一个像模像样的来源，而用户会以为它查证过。这与本项目「不产出看起来合理的错误」是同一条纪律。

**做法**
1. 检索到的 chunk 在提示词里编号成 `[S1]`…`[Sn]`，并附上它的真实出处（文件 + 章节）。
2. 模型的结构化输出里**没有 citation 字段**，只有一个 `source_ids: ["S1","S3"]`。
3. 代码按编号映射回真实出处（`citation`，形如 `装修合同审核 / 定金订金类 § 3. 现实情况`）；编造的编号被**剔除**并记入 `invented_citations`，同时写进 `data_gaps` 告知用户。
4. **允许留空**：常识性判断的 `source_ids` 可以是空数组，测试里有一条明确断言"留空不算错"。

**结果**
`TestCitationMapping` 一组测试守住它：有效编号映射成 § 章节出处；写了 `S9`/`S99` 被剔除并记入 `invented_citations`；留空不报错但会统计"有 N 条风险没有知识库依据"；大小写与空格容错。真实报价单实测输出形如 `装修合同审核 / 定金订金类 § 3. 现实情况`。

**为什么体现能力**
这与 A-05 选材（只能指认候选商品 id）、A-03 房间对齐（对不上就剔除）是**同一套手法**：**模型只负责"指认"，代码负责"落地"**。它已经是本项目反复出现的模式，不是一次性技巧。而"允许留空"这条尤其体现判断力 —— 若把"没有引用"也判成违规，模型会倾向于**编一个来源来交差**，那正是要避免的。

**面试话术**
- 讲法："AC-06 要求引用知识库来源。如果让模型自由写来源，那条引用根本没法验证，它还可能编一个像模像样的。所以我把检索到的 chunk 编号成 S1、S2 交给它，它只能回编号，代码再映射回真实的文件和章节；编造的编号会被剔除、记进 invented_citations，用户也看得到。"
- 追问"那没有依据的判断怎么办" → 允许 source_ids 留空，测试里明确断言"留空不算错"。因为如果把没有引用也判成违规，模型就会编一个来源来交差 —— 那比没有来源更糟。
- 追问"这是不是只在这一处这么干" → 不是。A-05 只能指认候选商品 id、A-03 对不上房间就剔除，都是"模型指认、代码落地"，已经是一条模式。

## 23. AC-06 的门槛是「≥5 类」不是「≥5 条」—— 所以"类"必须可数

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 避坑审查接入（AC-06）

**一句话亮点**：一条只说"识别 ≥5 类风险"的指标，如果不把类型固定下来，一个"把一个问题拆成十条"的实现也能达标 —— 可数性是**设计出来的**。

**背景 / 问题**
AC-06 只要求"识别 ≥5 类风险"。如果类型是自由文本，"类"就没法机械统计：一个把同一个问题拆成十条的实现，也能声称"识别了 10 类"。

**做法**
`risk_type` 用 `Literal` 枚举固定为 8 类（增项风险 / 漏项 / 单价异常 / 计价陷阱 / 模糊计量 / 环保风险 / 合同条款风险 / 营销话术）。验收时直接 `len({f.risk_type for f in findings})`，`ac06_met = distinct_type_count >= 5`。

**结果**
`test_同类型重复不算多类`：构造 10 条同类型的风险，断言 `distinct_type_count == 1` 且 `ac06_met is False`。`test_五类达标` 反向守住达标路径；`test_未达标不抛错只如实标记` 说明"未达标"是数据结论、不是运行失败。

**为什么体现能力**
**指标要能被"刷"就不叫指标。** 大多数人对验收指标的处理是"让它亮绿灯"，而这里我先问了一句"这个数字能不能被糊弄过去"。把枚举写进 Schema 不是装饰 —— 它让"≥5 类"从一个形容词变成一次集合运算，也让测试可以断言反面（10 条同类型不算 5 类）。

**面试话术**
- 讲法："AC-06 要求识别五类风险。这条很容易被刷 —— 把一个问题拆成十条，也能说识别了十条。所以我把风险类型用枚举固定成八类，验收时直接统计集合大小，还专门写了条测试：十条同类型的风险，必须判成只有一类、未达标。"
- 追问"为什么不用模型自报的类别" → 自报的类别不可机械统计，也没法断言反面。枚举化之后"类"是一次集合运算，指标才可判别。
- 追问"枚举八类够用吗" → 八类是按语料的实际结构定的，样本里埋了全部八类；枚举同时也会阻止模型自创一个没人能统计的类型。

## 24. 带标注的样本 + 可审计的召回率 —— 把 AC-06 从"感觉"变成"数字"

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 避坑审查接入（验收数据 `seed_data/sample_quotes/`）

**一句话亮点**：AC-06 有个陷阱 —— **它只要求"识别"，不要求"识别对"**；没有带标注的样本，你永远不知道模型是识别了 5 条还是编了 5 条。

**背景 / 问题**
「识别 ≥5 类风险」这句话背后的意思是"审得准"，但字面上一个把所有条目都报成风险的实现也能过。要有说服力，必须把"识别对了没有"变成可量化的数字。

**做法**
1. 造一份**合成报价单** `seed_data/sample_quotes/quote_01_economy.md`，埋了 14 条已知问题、覆盖 8 类风险。
2. 配套 `quote_01_economy.expected.json` 是**答案**，明确标注"仅测试与验收使用，不进 RAG、不给模型看"。
3. 一个关键设计：两条『单价异常』**锚定在 `material_catalog.json` 的演示区间上，因此客观可核验** —— 报价 218 元/㎡ 高于目录区间 99-179 的上限，1180 元/樘 高于 680-1080 的上限。测试 `test_可核验埋点确实成立` 会**重新查目录**确认这个不等式成立，保证答案文件不会因材料目录变更而**静默失效**。
4. 另一个关键设计：**匹配用显式 `match_keywords`，不用语义相似度**。否则"算不算命中"本身就成了主观判断，召回率也就没有说服力。

**结果**
`scripts/review_sample_quote.py` 实测：**召回 13/14 = 93%，8 类风险全部命中**；脚本口径下"未对应到埋点的风险项"为 0 条。AC-06 三项判定全部通过（≥5 类 / 召回 ≥50% / 有带依据的引用）。

**为什么体现能力**
这是"先让指标可测，再谈达标"的又一次实践（第 13 章讲过 AC-18 的同类做法）。这次更进一步：**连"怎么算命中"都要可审计** —— 用关键词而不是语义相似度，是为了让第三方（面试官）能自己复核这个 93% 是怎么来的，而不是听我说。

**面试话术**
- 讲法："AC-06 只要求识别五类风险，不要求识别对。所以我做了一份埋了 14 个已知问题的合成报价单，配一份答案文件，写脚本算召回率 —— 实测 13/14，93%，八类全中。这份答案故意不进 RAG、不给模型看。"
- 追问"命中判定怎么保证不是你自己说了算" → 每条埋点给了显式关键词，命中靠关键词匹配而不是语义相似度，否则"算不算命中"本身就是主观判断，召回率就没有说服力了。
- 追问"答案文件会不会过时" → 有两条单价异常锚定在材料目录的价格区间上，测试会重新查目录确认『报价高于上限』这个不等式仍然成立，目录一改测试就报红，不会静默失效。

## 25. 指标暴露的是输入缺口，不是模型能力问题 —— 诊断顺序：输入 → 工具 → 提示词

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 验收脚本首次跑分后的排查

**一句话亮点**：第一次跑分召回 12/14，漏掉的**恰好是那两条最客观、最可核验的**『单价异常』；排查后确认**不是模型能力问题，是输入缺了** —— 修法是补输入，不是改提示词。

**背景 / 问题**
漏掉的两条恰恰是答案里唯一**锚定在客观价格区间**上的（218 元/㎡ vs 99-179）。看起来反常：最客观的反而审不出来。

**根因**
报价单里写着"圣象地板 218 元/㎡"，A-06 **看到了这个数**，但**不知道这个型号的合理区间是多少**。没有基准价，"218 是贵还是便宜"这个判断它**再努力也做不出来** —— 就像一个没有参照物的裁判，再怎么盯着也判不出"这球出界了没有"。

**修复**
**补输入**，不是改措辞：新增 `_price_benchmark()`，把 `material_catalog.json` 的价格区间注入提示词（并如实带着"演示数据"的口径）；提示词里同时加一句纪律 —— **没有参考价可比的项，就不要报单价异常**，凭印象说"这个价偏高"不可靠。补上之后召回 **12/14 → 13/14**。

**为什么体现能力（本条最值得讲）**
遇到"模型做不对"，第一反应通常是调提示词。但应该先问一句：**"它拿到的信息够不够做这个判断？"** 缺信息时怎么调提示词都是徒劳，而且会一直调不好还找不到原因。**诊断顺序应该是：输入 → 工具 → 提示词，而不是反过来。** 这条不只适用于 LLM 应用 —— 一个函数返回结果不对时，先怀疑它拿到的参数，也是同一个顺序。

**面试话术**
- 讲法："第一次跑验收脚本召回 12/14，漏掉的恰好是两条『单价异常』—— 而那两条是答案里唯一客观可核验的。查下来发现：报价单里写着地板 218 一平，模型看到了这个数，但不知道这个型号的合理区间，所以它没法判断 218 是贵还是便宜。这不是模型能力问题，是输入缺了。"
- 追问"那你怎么修的" → 补输入，把材料目录的价格区间注入提示词，召回从 12/14 变成 13/14。我没有去改提示词的措辞 —— 缺信息的时候改措辞是徒劳的。
- 追问"你从中总结出什么" → 遇到"模型做不对"，先问它拿到的信息够不够，再怀疑工具，最后才是提示词。顺序反了会一直调不好还找不到原因。
- 追问"注入价格区间会不会让模型瞎报" → 提示词里同时加了纪律：没有参考价可比的项不许报单价异常，凭印象说"偏高"不可靠、宁可不报。

## 26. 两个不会报错、只会出错的 Chroma 坑

**日期 / 阶段**：2026-09-22 · 阶段1 · 知识库（Chroma + Ollama embedding）建成

**一句话亮点**：这两个坑的共同点是**它们不报错** —— 不会让系统崩，只会让结果悄悄变差，而"结果变差"极难归因。

**坑 1：Chroma 的 metadata 不支持列表值**
我们的 chunk 带 `tags: [报价审核, 增项]`，直接塞进去会抛 `ValueError`。麻烦在于它**只在"写"的时候炸** —— 等发现时可能已经写了一半数据，落一个半死不活的库。修法：写入时 `"|".join(...)`，读出时 `split` 还原（`tags_to_str` / `tags_from_str` 一对纯函数）。

**坑 2：不给 `embeddings=`，Chroma 会自己去下载一个默认 ONNX 模型（384 维）**
本机 `huggingface.co` 直连不通（实测基线），那一步会卡很久然后失败；**更糟的是它可能成功** —— 然后你得到一个 384 维的库，而查询用的是 Ollama 的 1024 维，维度不匹配才发现，中间所有检索结果都是垃圾。所以本模块**一律显式传 embeddings**，并在 `embed_texts` 里做维度校验。

**相关的一个"一次性决定"**
距离函数在建 collection 时定死（`hnsw:space=cosine`），因为 bge 是在归一化向量上训练的，用 L2 距离会把"向量长度"混进相似度。**建完改不了** —— 这类"一次性决定"必须在建库时就想到。

**为什么体现能力**
**这类坑的共同点是"不报错"。** 它们不产红、不抛异常，只让检索结果悄悄变差；而要归因"结果为什么变差"，你得先怀疑切块、再怀疑 embedding、再怀疑 prompt —— 每一步都很难证伪。所以在写这个模块时就把它们连同**原因**写进模块头注释，而不是等下次有人重建库时再踩一遍。

**面试话术**
- 讲法："接 Chroma 时踩了两个不报错的坑。一是它的 metadata 不支持列表值，我们的 chunk 带 tags，直接塞进去会抛错 —— 而且只在写的时候炸，发现时可能已经写了一半数据。二是如果不显式传 embeddings，Chroma 会自己去下一个 384 维的默认模型；本机连不上 HuggingFace，严重的是它可能下成功，然后你得到一个 384 维的库、查询是 1024 维，维度不匹配才发现，中间所有结果都是垃圾。"
- 追问"为什么强调不报错" → 它们不会让系统崩，只会让结果悄悄变差。而"结果变差"极难归因，你得先怀疑切块、再怀疑 embedding、再怀疑提示词。所以我把这两个坑和原因一起写进了模块头注释。
- 追问"距离函数为什么用余弦" → bge 是在归一化向量上训练的，L2 会把向量长度混进相似度；这个参数建 collection 时就定死了，建完改不了，属于必须一次想对的决定。

## 27. 检索层的一条纪律：`search()` 永远不抛异常；依据还必须封顶

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 检索层（`services/knowledge/retriever.py`）

**一句话亮点**：知识库不可用时返回**空结果 + 原因**而不是抛异常 —— 因为 A-06 该做的是如实说"本次未取得知识库依据"，**而不是凭常识编几条规则**。

**背景 / 设计**
AC-06 要求引用来源。**一个编造的"依据"比"没有依据"糟糕得多** —— 如果来源是编的，那条引用比没有引用更误导人（用户会以为是查证过的）。所以检索层的职责是：能查到就给带出处的 chunk，查不到就诚实地说查不到；`RetrievalResult` 带 `available` 与 `reason`，让调用方能区分"库挂了"和"没查到"。

**实测佐证：依据太多不只是浪费 token**
某次跑分时 `source_count=26` —— 检索没封顶。因为 A-06 会并发 13 个查询（5 个主题 + 8 个从报价单抽出的分项名），每个取 3 条，去重后仍有 26 条，是 `top_k` 的 2.6 倍。后果有两个，都很难归因：**提示词暴涨，模型 45 秒内写不完十几条风险，直接超时、产出 0 条**；以及依据太多会**稀释模型的注意力**，反而更容易漏掉关键项。修法：给 `search_many` 加 `max_total` 参数，`RETRIEVAL_TOP_K = 10`。

**结果**
知识库不可用时 A-06 照常审查、只是标记降级并把置信度压到 ≤0.4、在 `data_gaps` 里说明缺依据（有测试覆盖）；检索层单测覆盖了"库挂了"与"库好但没查到"两种情形。

**为什么体现能力**
**"检索越多越好"是个直觉陷阱。** 依据太多不只是成本问题，它会稀释注意力、拖慢生成，最后反而更容易漏掉关键项 —— 也就是说，一个"更慷慨"的检索配置会让**指标变差**。能识破这类反直觉，靠的是把"模型超时"和"产出为空"当成信号去追根因，而不是简单地把超时调大。

**面试话术**
- 讲法："知识库不可用时，检索层不抛异常，而是返回空结果加原因。因为 A-06 该做的是如实说本次没有取得依据，而不是凭常识编几条规则 —— 一个编造的'依据'比没有依据糟糕得多。"
- 追问"依据条数你设多少" → 封顶 10 条。有一次没封顶，检索出 26 条，提示词暴涨，模型 45 秒内写不完十几条风险、直接超时产出 0 条；而且依据太多会稀释注意力，反而更容易漏掉关键项。所以检索不是越多越好。
- 追问"既然不抛异常，怎么知道库是好是坏" → 返回结果里带 available 和 reason，能区分"库挂了"和"库里没查到相关内容"，两者对用户的说法不一样。

## 28. 网络绊线设错了位置 —— 同类问题第二次出现

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 接入后暴露

**一句话亮点**：第一版绊线守在某个**调用点**上；接入新模块后它自己 import 了 httpx，**新开了一条路，绕过了旧绊线** —— 而且症状和绊线最初要防的问题一模一样：不报错，只是变慢。

**背景 / 问题**
第 2 章讲过第一次绊线（测试静默打真实付费 API）。第一版设在 `llm_client.httpx.AsyncClient` 这一层 —— 守住了 LLM 那条路。第二次翻车：接入 A-06 后，`services/knowledge/store.py` **自己 import 了 httpx**，并用 `httpx.Client` 调 Ollama。测试于是真的去打了本机 Ollama，表现是某个"应该在 0.6s 内完成"的并发测试跑了 **4.93s** —— **不报错，只是变慢**。

**修复**
改为在 **httpx 模块级**替换 `Client` / `AsyncClient` 两个类。任何模块、任何写法，只要真的想出网都会撞上。报错信息直接指向两个最可能的原因（Agent 没被替换 / 新增了走网络的模块）和修法，并对 `@pytest.mark.integration` 显式放行。

**为什么体现能力（本轮的硬道理之一）**
**绊线必须守在"能力"上，而不是守在某个调用点上。** 守调用点的话，每加一个模块就多一个漏口；而漏口不报错、只是变慢 —— **和这个绊线最初要防的问题一模一样**。这是一个"防线本身要有正确抽象层级"的例子：修的不是那条漏网的路，而是选错了防守的位置。同理，`store.py` 里的 embedding 调用被拦之后，测试里的知识库 fixture 也必须打桩，否则所有工作流测试都会走"知识库不可用"的降级分支、正常路径反而没被测到。

**面试话术**
- 讲法："我们测试里有一条网络绊线，禁止测试打真实 API。第一版设在 LLM 客户端的 httpx.AsyncClient 那一层，守住了 LLM。接 A-06 的时候，新的向量库模块自己 import 了 httpx 去调本机 Ollama，等于新开了一条路绕过了旧绊线 —— 表现是某个本该 0.6 秒的测试跑了 4.9 秒，不报错，只是变慢。"
- 追问"怎么修的" → 改成在 httpx 模块级替换 Client 和 AsyncClient 两个类，任何模块任何写法只要真的出网都会撞上。绊线要守在"能力"上，不是守在某个调用点上。
- 追问"为什么这个值得讲" → 漏口不报错、只是变慢 —— 这和绊线最初要防的问题一模一样。说明防线本身也要有正确的抽象层级，光修那条漏网的路不够。

## 29. 把逐条子错误带进异常信息 —— 一次就定位到问题

**日期 / 阶段**：2026-09-22 · 阶段1 · A-06 接入调试期

**一句话亮点**：`_review_plans` 在三套方案全部审查失败时抛"所有方案的避坑审查均失败…"—— 这句话**把三条子错误全吞了**，排查只能靠猜。

**背景 / 问题**
`asyncio.gather(..., return_exceptions=True)` 已经把每套方案的子异常收在手里，但旧实现只判断"有没有成功产出"，全失败时抛一句笼统的 `ValueError("所有方案的避坑审查均失败，无可交付内容…")` —— 三个子错误被丢掉，排查变成猜谜。

**修复**
把 gather 收集到的逐条错误拼进异常消息：`f"所有方案的避坑审查均失败，无可交付内容 —— {detail}"`，`detail` 是三条子消息的拼接。改完后**一次就看到根因**：`TypeError: _stub() got an unexpected keyword argument 'max_total'` —— 测试桩没跟上我给 `search_many` 加的新参数。随后把测试桩的签名改成接受 `**kwargs`，避免同类问题再犯。

**为什么体现能力**
**"全部失败"这种聚合异常如果丢掉子原因，会把一次定位变成一场猜谜。** 错误信息本身就是调试工具 —— 写的时候要想到"半年后看到这句话的人能不能自己往下查"。这条与第 10 章「报错误的原因比报错本身更糟」是同一个方向的纪律：只不过那次错在**给用户的解释**，这次错在**给开发者的信号**。

**面试话术**
- 讲法："A-06 有个分支是三套方案全部审查失败时抛异常。第一版只抛一句'所有方案均失败'，把三条子错误全吞了，我只能猜为什么全失败。后来把 gather 收到的逐条原因拼进异常消息，一改完就一次看到根因：测试桩没跟上我新加的一个参数，报了 TypeError。"
- 追问"这算 bug 还是改体验" → 功能上它一直是"正确失败"，但错误信息本身就是调试工具。丢掉子原因会把一次定位变成猜谜，这和"报错误的原因比报错本身更糟"是同一类问题，方向是给开发者的信号。
- 追问"后来怎么防" → 把测试桩的签名改成接受任意关键字参数，桩没跟上真实函数时不会再在**被测代码**里炸一个离根因很远的错。
